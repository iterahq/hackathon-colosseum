The route file (`apps/mobile/app/[...path].tsx`) is composition: `ShellRoute` (launch gate: it calls `useLaunchConfig`) renders `WebShell`, which wires in-file hooks, one per concern: `useBridgeChannel` (the one `onMessage`: it stores the two buckets and performs the effect `receiveShellMessage` names; the router), `useNativeSessionLink` (the asker and the foreground revalidation), `useSessionProbe` (development), `useDflAuthSession` (the system auth sheet of the DFL sign-in, R-20), `useBlockedNotice` (one blocked-navigation notice at a time for the tap guard and the late guard) and `useNavigationGuard`. They stay in that file on purpose: a `.ts` outside `shell_chrome` may not import `react` or `react-native` (rule 1), `onMessage` and `nativeEvent` are read in the route file only (rule 1c), and `scripts/mobile/shell-route.test.ts` reads that one file. Moving a hook to its own file means a new name in `shell_chrome` (CODEOWNERS) and moving its pins with it. The decisions inside the route are pure functions with behaviour tests, and `shell-route.test.ts` keeps only the wiring that calls them: `nextEntry` (`routeEntry.ts`), `routerArrival` / `sessionReturnToLoad` (`dflAuthSession.ts`), `rereadOnForeground` (`shellGate.ts`), `backEffect` (`backConfirm.ts`). `app/+native-intent.ts` is run by `src/nativeIntent.test.ts` (in `src/` on purpose: Expo Router bundles every `.ts` under `app/` as a route, `expo-router/_ctx.android.js`).

Navigation guard, two lines. (1) `onShouldStartLoadWithRequest` runs `navigationDecision` on each request. The frame is read once, by `isTopFrameRequest`: Android's normal path sends no `isTopFrame` (`RNCWebViewClient.java` `createWebViewEvent`; only the fallback `TopShouldStartLoadWithRequestEvent.kt:18` sets it), so `undefined` is the top frame and only an explicit `false` (iOS) is a sub-frame; the sub-frame rules therefore hold on iOS only. (2) Android answers the request from a native thread that waits 250 ms for JS and, past that, loads the page (`RNCWebViewClient.java:111-113`, "defaulting to allow loading"). So `onNavigationStateChange`, which `onLoadStart` calls right after itself with the same event (`WebViewShared.js` `onLoadingStart`), judges the top-frame URL again with the same decision (`createLateGuard`, `shellChromeState.ts`): a page that is not `load` is stopped (`stopLoading()`), the WebView is created again on the last page the guard let through (reducer event `load`, the path of a relaunch) and a blocked one shows the same notice. The DFL handoff of an installed build is stopped too; Expo Go's allowed DFL origin (`DEV_TOP_FRAME_ORIGINS`) is not judged. Recoveries are counted per last good page inside 60 s (not reset when a page finishes, so an app page that redirects out after loading still trips it); the fourth shows the failure card at once, with its two buttons (`LATE_GUARD_ERROR` through the reducer's `error`), and no new relaunch. Inherent cost: the late guard acts after the page was committed, so a recovery is a full relaunch of the last good route (in-page state is lost), and a late JS answer to the tap guard still performs its own effect (the browser or the auth sheet) in addition. Not measured on a phone.

Android route changes are not loads. On Android the only source of `onLoadStart` is `doUpdateVisitedHistory` (`RNCWebViewClient.java:74-82`; `onPageStarted`, `:85-91`, emits nothing to JS), which Chromium also calls for `history.pushState`, with `loading` false (`createWebViewEvent`, `:314-322`: `!mLastLoadFailed && getProgress() != 100`, and the progress of a same-document change is 100) and no `onPageFinished` after it. `WebViewShared.js` `onLoadingStart` then calls `onLoadStart` and `onNavigationStateChange` with that event. Before `classifyLoadStart` the shell treated each of those as a load: veil, the 15 s timer (no `loadEnd` ever came) and so the failure card on the first route change of a session, plus `shellBridge.reset()` (the router session, keep-awake and the native session copy dropped on every route change). Now an Android start with `loading: false` on a `ready` page is a history update: the URL and `canGoBack` change and nothing else. iOS is not affected (`WKWebView` sends no policy event for pushState, and its `loading` is false at the policy decision of a real navigation, so iOS always starts a load). Not measured on a phone.

Update card and mounted pages: a re-read that turns run into update (a raised `minShellVersion`) is not applied under a mounted page, because the card would unmount the WebView and the learner's in-memory state (`shownLaunch`). It applies at the next launch or the next route entry (a new `entryPath`), or at once when the failure card's Retry started the read (the page is already gone).

Both Retry and a process death create a new WebView (a React `key`) instead of calling `reload()`: a dead Android renderer cannot be reloaded, and one path then serves every failure. `onHttpError` fires for the main frame only on both platforms (`RNCWebViewImpl.m` `forMainFrame` at v13.16.1; `RNCWebViewClient.java:267`), so a failing API call or image never shows the card. iOS fills `description` with `localizedDescription` (`RNCWebViewImpl.m:1510`), so on a non-English phone the text never matches; the locale-free `code` and `domain` decide first. Not measured on a phone: which code airplane mode and a Wi-Fi without internet report (a miss shows the generic card, never nothing).

## Console forwarder (ADR-5 "Consequence")

`apps/mobile/src/consoleForwarder.injected.ts` is a script string injected with `injectedJavaScriptBeforeContentLoaded` plus `injectedJavaScriptBeforeContentLoadedForMainFrameOnly={true}` and `injectedJavaScriptForMainFrameOnly={true}`, so boot errors are counted. `apps/mobile/src/consoleMessage.ts` fills in the origin and the redaction rules (`buildConsoleForwarder`; the rules are its own `REDACTIONS` list, so a new secret shape is added once and the test compares the built script's output with `redactSecrets`) and holds the console reader, `readConsoleShape` (the frame is proved before it, by `messageSize`). The 500-character limit is `MAX_TEXT_CHARS` there, and the script is built from it like the redaction rules. Each constraint is tested in `consoleMessage.test.ts` by running the built script in a bare sandbox:

| Constraint | Where |
|---|---|
| Attaches only when `location.origin` is the app origin | the script's first check |
| Redacts `(access\|refresh\|dfl)_token` and `code=` values, api-key values, bearer tokens, JWT-shaped and `sb_publishable_`/`sb_secret_` strings, e-mail addresses, before posting | the script's `redact`, again in `redactSecrets` of the parser |
| `onMessage` drops a message whose frame URL is not on the app origin, or that is not `{type:'console', level, text}` | `receiveShellMessage`: `messageSize` (the frame, `messageWindow.ts`) and `readConsoleShape` (the shape) |
| Size: text cut to 500 characters, a message over 4096 characters dropped | script and parser |
| Rate: at most 5 messages per second and 50 per page load in the page; at most 10 per second natively | the script; `admitMessage` (`messageWindow.ts`) |
| Development only: in a release build the script is not injected and the console shape is not parsed. `onMessage` itself is always set since R-6 (the bridge needs it) | the route file (`__DEV__`) |
| Forwards only `console.error`, uncaught errors and unhandled rejections | the script |

v1 capabilities: `shell.version` and `keepAwake` (R-8); shell 0.3.0 adds `auth.session` (R-12, section below; the rest of this paragraph is the R-6/R-8 text). A method of the protocol without a handler (`link.open`, `haptics`, ...) answers `capability_absent`; no navigation command, no file access. ## One-copy rules

`scripts/mobile/one-copy.test.ts` runs in the `build-test` job. The rules live in `scripts/mobile/oneCopyRules.ts`; each rule has a negative fixture in the test. A PR that touches `apps/mobile/route-map.json` needs Tainan's review (CODEOWNERS is a record, not a gate).

1. Every `.tsx` under `apps/mobile/` is in `shell_chrome`, or is a route file of at most 15 lines that only renders an export of `@iterahq/screens`. ### Keep awake (R-8)

The screen stays on during `/lesson/:lessonId` and `/live/*` only. The one call site is `KeepAwakeRouteMount` (`src/lib/shellKeepAwake.ts`), mounted beside `ShellBridgeMount`: it calls `keepAwake {on: true}` when the router enters one of those routes and `{on: false}` when it leaves or unmounts. In a browser tab the handshake settles at `no_shell` and nothing is sent; the Screen Wake Lock API is out of scope. In the shell, `apps/mobile/src/keepAwakeHolder.ts` holds the lock under one tag (`expo-keep-awake`) and one registry holds the one platform lock per process and each mounted WebView holds its own claim, so a hidden WebView's release never drops another's claim. `bridge.reset()` releases the claim: on each accepted `hello` (a new session never inherits a lock), on each top-frame load start, on WebView relaunch (Retry, process death) and on unmount. The payload is `{on: boolean}` and nothing else; any other shape is `bad_payload`. `useKeepAwake()` of PR-2 is gone.

### Launch gate and `shell-config.json` (R-7)

`public/shell-config.json` is served by the web deploy at `<webOrigin>/shell-config.json` with `Cache-Control: no-cache` (the `location = /shell-config.json` block of the nginx config in the `Dockerfile`; a missing file is a 404). Keys: `minShellVersion` (`x.y.z`), `updateUrl` (`null`, or `{ "ios": url|null, "android": url|null }`: iOS only `https://apps.apple.com/...`, Android only `https://play.google.com/store/apps/details...`, read by `apps/mobile/src/shellGate.ts`, so `packages/bridge` stays byte-identical to upstream), `forceWebview` (route patterns). Shipped values are neutral: `"0.0.0"`, `null`, `[]`; Tainan owns the values and the shape (`/public/shell-config.json` is in CODEOWNERS), and a test bounds them (`minShellVersion` not above the newest `packages/bridge/contracts/shells/*.json`, `forceWebview` entries are routes of `apps/mobile/route-map.json`).

The shell reads the file at launch with `fetch` and `no-store`, in parallel with the WebView (no added latency; 4 s timeout, 16 KiB cap, app origin only, no URL taken from the file). Every failure to read it (no file, HTTP error, timeout, offline, malformed or oversized body, a redirect to another origin) restricts nothing. Closed by design: a valid `minShellVersion` above the shell replaces the WebView with the full-screen update card (`apps/mobile/src/UpdateNowCard.tsx`); the store button appears only for a vetted URL of the running platform, and the card is complete without it ("Uma atualização é necessária. Fale com quem te passou o app."). The card is not terminal: the config is read again when the app returns to the foreground and on "Tentar de novo"; a config that was read and no longer restricts lifts the card, a read that fails keeps it. A launch with no network reads again too (`ReadStatus` of `createLaunchGate`, `rereadDue`): on a return to the foreground 30 s after a failed read, and 30 min after a successful one (a raised `minShellVersion` is seen within half an hour; switching apps does not fetch every time), and on the failure card's "Tentar de novo" when the last read failed. Reads are numbered when they start, and a read that settles after a newer one cannot overwrite it. Rollback latency (CI + deploy until a launch sees the file) is not measured. There is no `billing.external` (Q-3).

Known limits of `forceWebview`, owned by R-13 (not built): (a) it matches the bundled route pattern exactly, so `/Catalog`, `/program/:id` or a concrete `/program/abc` are silent no-ops; (b) it fails open on a timeout, so on a slow network a broken native route still opens (persist the last good list); (c) `LaunchConfig.forceWebview` is not threaded to any consumer, because no native route exists; (d) the pinned bridge copy still exports `hasShellCapability` and parses a remote `capabilities` list, an upgrade path ADR-7 forbids: `decideLaunch` drops it, and R-13 adds a one-copy rule that `apps/mobile` never imports `hasShellCapability`.

Threats (PLAN section 8, item 4):

| Sender | What it can do | Why not more |
|---|---|---|
| A sandboxed frame of learner code (`sandbox="allow-scripts"`, `srcdoc`), iOS and Android on the `WebMessageListener` path | nothing | its origin is opaque (`about:srcdoc` / `null`): `messageSize` drops it before the raw window, before either reader and before any router, with no reply. It cannot deliver a token, reset the handshake, starve the page's messages, or read a reply |
| The same frame on an Android System WebView without `WebMessageListener` (every frame is reported as the top frame) | handshake with the router that has no `auth.session`; replace THAT handshake (the R-8 keep-awake limit, unchanged); use up the raw window (40 messages or 256 KiB per second reach a parser, never more) | `auth.session` is not registered on that router: the handshake does not list it, a call answers `capability_absent`, the shell never asks. No token is ever held on that path |
| A frame or page on another origin | nothing | `foreign_origin`, no reply; a reply is posted with the app origin as `targetOrigin` |
| A sub-frame on the app origin itself, or script injected in the page (XSS) | everything the page can: read the handshake reply, forge `auth.session`, sign the shell out | **not defended, and it cannot be from JavaScript**: both platforms know whether the sender is the main frame, but react-native-webview 13.16.1 discards it and reports none (a patch upstream, or a native module, would close this; neither fits Expo Go). Such script already reads the Supabase session (refresh token included) from the page's storage, so the bridge gives it nothing new. `src/` renders no same-origin sub-frame today |
| A fake shell: a browser extension or a hostile app that defines `window.ReactNativeWebView` and answers `HelloAck` with `auth.session` | receive the learner's **access token** (about an hour of life), again on each refresh | nothing in the handshake proves a shell is genuine, so the page does post the token (`src/lib/shellAuthSession.test.ts` states it). Whoever can define that object on the app's window runs script in the page or owns the WebView: it can read the whole session, refresh token included, without the bridge. A page that merely embeds the app cannot: the object must be on the app's own window, and `frame-ancestors` limits who frames it |
| Logs | — | the new shell code has no `console` call; the host logs a refusal REASON only; a refusal detail is scrubbed of the held token and of JWT-shaped runs; the console forwarder's redaction now also covers a token cut short. React state holds the expiry, never the token |

How the legacy Android path is known: not from a WebView version (a threshold would be a guess) but from the message itself. On the `WebMessageListener` path the library reports the ORIGIN of the sender frame (`https://app.iterahq.dev`, no path); on the fallback it reports the URL of the top frame, which always has a path. `senderAttributed` (`apps/mobile/src/bridgeMessage.ts`) takes an Android message as attributed only when its URL is exactly the app origin. If that reading of the library is wrong on a device, the failure is closed: Android is never offered `auth.session`, and the overlay says `Sessão: não oferecida (este WebView não informa o frame)`.

The three limits R-6 left to this row: (1) Android legacy frame attribution: closed for the token as above (not for keep-awake). (2) A same-origin sub-frame: not closable from JavaScript, stated above. (3) `Math.random` session token: replaced by 256 bits from `expo-crypto` `getRandomValues` (`apps/mobile/src/sessionToken.ts`), ask ids too; the replay window stays 1024 ids, because whoever can capture a call also reads the session token inside it and needs no replay.

Also changed: `onMessage` has two windows. `messageSize` (in `apps/mobile/src/messageWindow.ts`, no parse) drops a frame that is not on the app origin: it is counted nowhere, so a learner's preview frame that posts in a loop can no longer make the shell drop the page's own messages (before, it shared the page's 10 per second). `admitRaw` then admits at most 40 messages and 256 KiB per second to the parsers, which bounds `JSON.parse` on the Android legacy path, where every frame passes the origin gate. The page's budget (`admitMessage`, 10 per second) comes after the parse and counts only what a parser accepted.

Matrix: new web + shell 0.2.0 or older: `auth.session` is not listed, the page sends nothing. Shell 0.3.0 + a web build without this row: no token ever arrives; the probe shows `Backend: —`, the session line `Sessão: não`.

Known limits: a hidden second WebView (a deep link over an open route) shares the one copy, last writer wins, and the page asked for a fresh token is the one mounted last (when that WebView unmounts, the one beneath it is asked again); Android hardware back reaches every mounted route (`BackHandler` calls them newest first), so the one that is not focused leaves the press (`decideBack`, `focused`), and the focused one at its page root leaves it to the navigator when a route lies beneath (`canPop`; the pop is read from the library source, not run on a device); a sign-out lost three times in a row while the app stays in the foreground leaves the copy until its `exp` or the next top-frame load (the next return to the foreground ends it); one-copy rule 1b for `apps/mobile/src/backendProbe.ts` ("exactly one `fetch(`, no host literal") is a tripwire read by a reviewer, not a guarantee: `const f = fetch; f(url)`, `globalThis['fetch'](url)`, a host assembled from pieces (`'https:' + '//host'`), a decoded one (`atob(...)`) and `new Function('return fetch')()` all pass it unchanged (rule 1c still closes `XMLHttpRequest`, `WebSocket` and `expo/fetch` in every shell file, and a `fetch(` in any other file); on the Android legacy path a frame can still spend the raw window, so the page's messages can be dropped there (no token exists on that path); React Native's `fetch` follows redirects and that cannot be turned off from JavaScript (the probe discards an answer that came from another origin; PostgREST does not redirect). Not verified on a device: everything in this section.

### Recipe

1. Add the row to `apps/mobile/route-map.json`: `screen: "<screen>"`, `universal: true`, `mode: "webview"`, `web_paths` = the page files you are about to delete.
2. Write `packages/screens/src/<screen>/<Name>Screen.tsx` with `View` / `Text` from `react-native` and `className`. No HTML tag, no `window`/`document`, no hook of a router or of a data client: what the screen needs from its host is a prop typed by a port of `@iterahq/shell-core`.
3. Give every `Text` its `font-sans`, size and colour class: a `Text` inherits nothing (react-native-web resets it to 14 px black, React Native has no cascade). Headings (`role="heading" aria-level={n}`) take the display face from the web's base layer; leave the font class off.
4. Put a platform difference in `<screen>/slots/` and nowhere else (`Platform.OS` there, or `x.web.tsx` + `x.native.tsx` with named exports).

### What Uniwind / React Native cannot express, and what to do instead

| Web habit | On native | Instead |
|---|---|---|
| `grid`, `col-span-*`, `place-items-*` | no grid | `flex-row flex-wrap` with fixed basis, or a list component in a slot |

| `group`, `group-hover:`, `peer-*`, `[&_x]:` | no selectors across elements | state in the component, classes chosen in JS |
| `fixed`, `sticky` | no such position | the native header/tab slot, or `absolute` inside a full-screen `View` |
| `backdrop-*`, `blur` | not available | a translucent background colour |
| `animate-*`, `@keyframes`, `transition*` | not available | none, or an animation in a slot |

Android limit: a filter cannot exclude a path, so `/live/:sessionId` is NOT claimed on Android (a `/live/` prefix would swallow `/live/instructor`); on iOS it is claimed.

How the link reaches the page: Expo Router strips the origin of an https link and hands the catch-all route the path segments, the query as params and the fragment as the param `#`, and it DECODES them (`expo-router/build/hooks/useLocalSearchParams.js`; `?next=%252F` comes out as `?next=%2F`, `#…next=%2Fx` as `#…next=/x`). Rebuilding from those params is therefore not byte for byte. The route instead takes the RAW link from `app/+native-intent.ts` (`redirectSystemPath`, which Expo Router calls with the raw link on a cold and on a warm start before it parses it; read from `getLinkingConfig.js` and `link/linking.js`, not run on a device), kept in memory as the last link only (`src/rawLink.ts`; the DFL callback is forgotten once the route has taken it, R-20), after the refresh-token strip below. `entryFromLink` uses its query and fragment byte for byte when the link is https, exactly the app origin, and its path is the route being shown; the path itself is the canonical path of the route. When there is no such link (Expo Go's `exp://` link, a stale link of another path) `entryPathFor` rebuilds from the params: same meaning, not the same bytes (the limit is stated in `deepLink.ts`). A path that is not a route opens the home route and drops both. The path comes from the pathname, never from the `path` param, so a link with `?path=…` cannot pick the route (the key is dropped); a query key named `#` shares the router's fragment slot and is read as the fragment (same page, pinned in `deepLink.test.ts`). The route is keyed by the whole entry path, so a second link to the same page reloads it.

Refresh tokens (ADR-10: none reaches native code). The web's Supabase client sets no `flowType` (`src/lib/supabase/client.ts`), so auth e-mail links return on the IMPLICIT flow: the reset e-mail to `/auth/reset#access_token=…&refresh_token=…&type=recovery`, the magic link and OAuth to `/#access_token=…&refresh_token=…` (`passwordReset.service.ts`, `otpAuth.service.ts`, `AuthContext.tsx`). Two consequences. (1) `/auth/reset` is NOT claimed, on either OS: a reset finishes in the browser. `deep-links.test.ts` keeps a closed list of returns that carry a session on the implicit flow, with the reason, so one cannot come back by accident. (2) `/` cannot be unclaimed, so a query or a fragment that carries a `refresh_token` parameter is dropped whole: the page opens on the path alone. This is done at the intake, the one place that sees a link first: `app/+native-intent.ts` calls `intakeLink` (`src/deepLink.ts`), which returns such a link WITHOUT its query and fragment and remembers only that stripped form, so neither Expo Router (which would parse the token into params) nor `src/rawLink.ts` ever holds the token. It matches the parameter name in any casing, percent-encoded (`refresh%5Ftoken`) or nested in the fragment, handles full https, bare-path and `exp://` forms, and cannot throw (string slicing and regex tests); a value that is not a string gives `/` and remembers nothing. `entryFromLink` and `entryPathFor` repeat the check as the second line (`carriesRefreshToken`). **The plan's acceptance line for R-5, "a reset email opens the app at `/auth/reset`", is NOT met by this PR.** It waits for a decision: the web moves to PKCE (`?code=`, no refresh token on the link), or an explicit exception to ADR-10. `src/` is not changed here.

Credentials on a link: nothing stores or logs a URL. Found and fixed: the dev overlay printed the loaded URL (now `displayUrl`: `…/lesson/x?…`, never a value); the console redaction did not know a `code=` parameter (added to `redactSecrets` and to the injected script, kept for a PKCE flow that the web does not use today); "Open in browser" on an `/auth/` page would have put the query or fragment in the system browser's history (now `browserUrl` drops both there). Retry re-creates the WebView on the URL it was on, in memory only.

Android file: the fingerprint is the SHA-256 of the EAS-managed upload keystore (Expo org `iterahq`, read from the Expo API on 2026-10-07). It signs the preview APK. A build distributed by Google Play is re-signed by Play App Signing with another key: that second fingerprint must be ADDED to `assetlinks.json` when the Play Console app exists (owner: Tainan); until then a Play build does not verify.

The returned URL carries `#dfl_token=…`, a bearer DFL token (a captured link replays until expiry, as on the web today). It goes from the validator to the reducer and nowhere else: no `console.*` reads it (pinned in `shell-route.test.ts`: the file has exactly the two known console calls), a session that fails to open shows the one short notice "Não foi possível entrar com DFL" (never the error text or the URL), the dev overlay prints the URL through `displayUrl` (no query, no fragment), and nothing is stored on disk. In memory the callback URL (token included) can be held in these places, and no others: (1) `src/rawLink.ts`, from the moment the link arrives until the route has consumed it (`isCallbackEntry(rawEntry)`, an effect of `ShellRoute`, in either Android order), when `forgetLink` drops it; (2) the `entry` ref of `ShellRoute` (`raw`, and `effective` unless the latch called it a duplicate), for the life of the route; (3) the `loadedUrl` state and (4) the `lastGoodUrl` ref of `WebShell`, until the next navigation event or unmount; (5) the closure of the `openAuthSessionAsync` promise, until the session ends; plus the WebView's own URL. `restartUrl` never relaunches on it: Retry, process death, the late guard's recovery and "Abrir no navegador" all answer the app's home path for the callback. The one-copy rules hold unchanged (`one-copy.test.ts` passes with no closed list edited). A restart never lands on the callback: the page scrubs the fragment with `history.replaceState`, which iOS does not report, so `loadedUrl` can still hold the token URL; `restartUrl` (Retry, process death, "Open in browser") answers the app's home path for `/auth/dfl/callback` instead of replaying it.

State binding (login CSRF): the web binds the sign-in to the browser that started it through `next`. `loginWithDfl` stores a one-shot nonce in `localStorage` (`src/auth/dflState.ts`, valid 60 minutes, under a key outside the `itera.` prefix so `clearIteraStorage` keeps it) and sends `next=/~<nonce><path>`; the DFL page returns `next` unchanged and `DflCallbackPage` exchanges the token only when the nonce matches. `return` is still exactly `<app origin>/auth/dfl/callback`, so `isDflHandoff` and every build already shipped keep working, and an old shell needs nothing. A callback that was not started in this WebView shows a refusal with a one-tap restart (or goes home when already signed in). Not measured: that Android keeps the WebView `localStorage` between the system sheet and the return.

Not measured, needs an installed build on a phone (plan row 0.29, per OS): that the redirect inside the auth session returns to the app, fragment included.
- iOS: `expo-web-browser` takes the `ASWebAuthenticationSession` `.https(host:path:)` callback ONLY when `preferUniversalLinks` is true AND the OS is iOS 17.4 or later (`ios/WebAuthSession.swift`); otherwise it uses `callbackURLScheme: "https"`, which never intercepts. The route passes `{ preferUniversalLinks: true }`, so on iOS 17.4+ the session ends on `https://app.iterahq.dev/auth/dfl/callback` and the URL comes back to the shell. **iOS below 17.4 is NOT supported for DFL sign-in:** the scheme form never matches an https redirect, so the callback page loads inside the sheet, in Safari's context. With the state binding it shows the refusal there (the nonce lives in the WebView's storage, not Safari's). If the learner taps the restart in the sheet, a session IS created in Safari's context, the sheet stays open, and the shell stays on `/login`. Still unsupported. Not measured.
- Android: `preferUniversalLinks` has no effect there (the library reads it in the iOS code only; the Android path passes the options to `openBrowserAsync`, which ignores it). `expo-web-browser` has no native auth session there; it opens a Custom Tab and races a `Linking` `url` event against the tab closing. When the App Link opens the app, the same URL also reaches Expo Router (R-5), which would re-create `WebShell` on it while the session promise also loads it: the callback page could load, and exchange the token, twice. `createReturnLatch` (`dflAuthSession.ts`) lets exactly one load happen, whichever arrives first: the session's copy loads and the router's copy keeps the WebShell it has (same key); or the router's copy loads and the session's copy is dropped. The two copies are NOT compared as strings (Expo Router decodes its copy: `next=%2Fx` becomes `next=/x`, `useLocalSearchParams.js`): during a session, or within 5 s after the session loaded it, a callback-path arrival from the other source is the same return. The latch holds no URL and no digest, only which source loaded last and when; it clears when consumed, when the session ends (router-set), after 5 s, and when the next session begins. If the router's copy arrives first and the session then settles with `dismiss`, the router's copy has loaded alone. **This path was reasoned from the library source (`expo-web-browser` `WebBrowser.js`, `expo-router` `extractPathFromURL.js`) and was not run on a device.** The route reads the latch during render (a ref keyed by the link), which is idempotent but was not exercised under React StrictMode (the shell does not use it). The cancel-or-dismiss result can also win the race on Android: the router's copy then does the load alone. **Which route instance.** `usePathname()` is global (`expo-router/build/hooks/usePathname.js` -> `global-state/useRouteInfo.js`, one `routeInfo` in `global-state/store.js`, every subscriber notified), so every mounted instance of the catch-all re-renders with the FOCUSED route's pathname. An instance that is not focused (`useIsFocused()`) therefore keeps the entry it has (`nextEntry`, `src/routeEntry.ts`): before this, any warm deep link over `index` re-created the WebView beneath on the link's page and the DFL return re-created it on the callback WITHOUT its fragment. A normal launch sits on the route `index`; the stack router reuses a route for a link only when the route NAME matches (`StackRouter.js:191`), so the App Link that ends a sign-in started there PUSHES a new `[...path]` instance. The order Android is expected to produce is router first: the pushed instance loads the callback, the session's copy is the duplicate and is dropped, and the instance beneath keeps its page. If the session's copy arrives first, the pushed instance is `leaving` (defensive path: no WebShell, `router.back()`; with no route beneath it shows the entry); that path has not been run on a device. A sign-in started on a `[...path]` instance is reused by the link (same name). Not run on a device. Android also needs `assetlinks.json` (R-5) with the fingerprint of the key that signed the installed build.
- Whether a DFL sign-in started in mobile Safari or Chrome, with the app installed, still completes in the browser (the other half of row 0.29).
A "no" goes back to Tainan as a question (ADR-10): a web bounce to `itera://` would pass the token through a scheme any Android app can claim.
