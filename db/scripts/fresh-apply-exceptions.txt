# db/scripts/fresh-apply-exceptions.txt
#
# The declared deviations between "LC_ALL=C sort of db/migrations/*.sql" and a
# build order that actually works from an EMPTY database. Read by
# db/scripts/fresh-apply.sh.
#
# ⚠️ THIS FILE IS CLOSED TO NEW MIGRATIONS. fresh-apply.sh REFUSES a run in
# which a file added by the pull request appears here (exit 4). Every entry
# below is a fact about the pre-2026-08-07 past that cannot be edited away —
# see "why nothing can just be fixed" at the bottom. A new migration that does
# not build from zero is a broken migration; renumber or fix it.
#
# FORMAT — one directive per line, `#` starts a comment:
#
#   hoist <filename> before <anchor-filename>
#       Apply <filename> immediately before <anchor-filename> instead of at its
#       sorted position. Both files must exist.
#
#   skip <filename>
#       Do not apply <filename> at all.
#
# ─────────────────────────────────────────────────────────────────────────────
# 1. THE CONSOLIDATED itera-api / itera-mcp SERIES (PR #282, 2026-08-04)
# ─────────────────────────────────────────────────────────────────────────────
# PR #282 moved 14 migrations out of `itera-api` and `itera-mcp` into this
# series and renumbered them 0041–0054. The header of
# 0047_mcp0003_activity_status_draft_published.sql states the intent:
#
#     "The new number is the order in which it was ACTUALLY applied, which is
#      also its dependency order"
#
# MEASURED 2026-08-07 AGAINST AN EMPTY POSTGRES: that is not true. In sorted
# order, 0024_activity_defs_reusable_library.sql fails four times over —
#
#     itera.activity_status  (created by 0047_mcp0003)  -> column `status`
#     itera.media            (created by 0048_mcp0004)  -> FK thumbnail_media_id
#     itera.set_updated_at() (created by 0050_mcp0006)  -> trigger
#     itera.member_role 'author' (added by 0041_mcp0002) -> used by 0026
#
# — every one of them a reference FORWARD into the block that was numbered
# after it. None of the 14 files depends on anything created at 0024 or later
# (checked file by file), so the whole block moves ahead of 0024 as a unit.
# With that single move the entire series builds from zero, twice, clean.
#
# WHY NOTHING CAN JUST BE FIXED. itera.schema_migrations is keyed by FILENAME
# and carries a CHECKSUM. Renumbering an applied file makes it look unapplied
# and the next `db-apply` re-runs it against the ITERA production database;
# editing one trips checksum drift and `db-apply` then refuses to apply
# ANYTHING until a human rebaselines it. Both are worse than a declared,
# reviewed exception file. Tracked separately — see the issue linked from the
# PR that introduced this check.
#
# THIS IS NOT THE ORDER `db-apply` USES, AND IT NEVER COULD BE. `db-apply`
# applies only PENDING files onto the live schema; it has never built anything
# from zero and has no opinion about the order of files applied long ago. The
# order below is the one that reconstructs the schema, which is a different and
# newly-checkable claim.
hoist 0041_mcp0002_author_role_and_authoring_rls.sql       before 0024_activity_defs_reusable_library.sql

hoist 0047_mcp0003_activity_status_draft_published.sql     before 0024_activity_defs_reusable_library.sql
hoist 0048_mcp0004_media_registry.sql                      before 0024_activity_defs_reusable_library.sql

# 2. THE ONE FILE THAT CANNOT RUN ANYWHERE BUT PRODUCTION
# ─────────────────────────────────────────────────────────────────────────────
# 0005 inserts memberships against two HARD-CODED tenant UUIDs
# (96786037-… "itera" and 0618cad6-… "acme"). Those are the ids those rows
# happen to have in the ITERA production database. 0003_itera_seed.sql creates
# the same two tenants with `gen_random_uuid()` and no explicit id, so in any
# other database they have different ids and the FK fails:
#
#     ERROR: insert or update on table "memberships" violates foreign key
#            constraint "memberships_tenant_id_fkey"
#     DETAIL: Key (tenant_id)=(96786037-…) is not present in table "tenants".
#
# It is a verification FIXTURE, not schema — it creates no object, so skipping
# it costs the check nothing. It is also the reason a fixture like this should
# never have been a migration; new ones go through MCP (CLAUDE.md, DDL vs DML).
#
# ─────────────────────────────────────────────────────────────────────────────
# 2026-08-12 — "IT CREATES NO OBJECT" IS NOW MEASURED, NOT ASSERTED
# ─────────────────────────────────────────────────────────────────────────────
# That sentence was the whole justification for the skip, and nothing checked
# it. If anybody ever added DDL to this file, the skip would have hidden it in
# silence — a skipped file is exactly where a missing object is hardest to see.
#
# db/census/expected-schema.txt is generated from a build that omits 0005, and
# it matches the live ITERA database fact for fact across 933 catalogue facts:
# relations, columns, defaults, constraints, indexes, function bodies, RLS
# policy predicates, grants, triggers, publication membership and COMMENTs. So
# the claim is now a measurement. Put DDL in 0005 and schema-parity.sh goes red.
#
# WHY THE FILE ITSELF IS NOT FIXED. The two obvious repairs are to make 0005
# resolve the tenants by slug, or to make 0003 write the ids explicitly. Both
# EDIT AN ALREADY-APPLIED MIGRATION. itera.schema_migrations records a
# checksum, so the edited file no longer matches its ledger row, and
# apply-migrations.sh then REFUSES TO APPLY ANYTHING to production until a
# human runs `rebaseline`. The next merge of an unrelated migration would fail
# on a database that is perfectly healthy. Repairing a recovery path by
# breaking the live one is not a repair.
#
# WHAT IS FIXED INSTEAD, so this cannot happen again:
#   * db/scripts/check-no-invented-ids.sh refuses any NEW migration that
#     hard-codes a UUID without saying why. This defect is a class, and the
#     class is now closed even though this instance stays.
#   * apply-migrations.sh honours this file's order when it builds an EMPTY
#     database, and records a declared skip as `declared-skip:` in the ledger —
#     never as `applied`. A recovered database therefore reports 0 pending
#     instead of carrying 0005 as permanently outstanding.
skip 0005_tenant_admin_fixture.sql
